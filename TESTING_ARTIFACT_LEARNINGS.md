# Testing Artifact Learnings: AI-Native Development Pipeline

> Date: 2026-02-23
> Scope: v1.0.17 batch (7 tickets, 4 specs, 4 parallel agents, 5 E2E tests)
> Pipeline: /groom → /approve → parallel worktree agents → E2E write + run → artifacts

---

## Pipeline Audit: What Happened

| Phase | Duration | What Ran |

## What Worked

### 1. Ticket Grouping (7 → 4 Specs)
Grouping related tickets by file coupling reduced merge conflicts to zero:
- TRO-160/161/163/169 → `restaurant-onboarding-ux-fixes` (all touch claim flow + More tab)
- TRO-162 → `claim-approval-refresh` (isolated to AuthContext)
- TRO-170 → `multi-restaurant-claims` (isolated to services + dashboard)
- TRO-168 → `hide-communities-business` (isolated to tab screens)

**Optimization**: This grouping should be automated. An agent could analyze file overlap from ticket descriptions and suggest groupings.

### 2. Stakeholder Questions Prevented 100% Rework
All 4 specs would have been implemented with wrong scope without Q&A:
- Q1 UX fixes: User chose B (remove beta from BOTH flows), AI assumed A (claim only)
- Q1 refresh: User chose B (AppState + realtime), AI recommended A (AppState only)
- Q3 multi-restaurant: User chose A (include in v1.0.17), AI recommended deferring
- Q2 communities: User chose B (also hide Explore), AI recommended A (Home + Add only)

**Optimization**: Questions could be ranked by "risk of wrong default" to help stakeholders prioritize.

### 3. Worktree Isolation Eliminated Merge Conflicts
4 agents in parallel worktrees, 0 merge conflicts. The key was explicit "do NOT modify" boundaries in each agent prompt.

### 4. Pre-Implementation Codebase Exploration
Running 3 explore agents before grooming ensured:
- Exact file references (line numbers, function names)
- Discovery of existing infrastructure (RestaurantContext, RestaurantSwitcher already existed)
- Root cause identification (TRO-162 was AppState issue, not Supabase issue)
- Finding that TRO-160 was already fixed in current code

## What Didn't Work

### 1. E2E Tests Required Heavy Manual Iteration
The agent-generated E2E tests (basic stubs) all failed on first run:

| Issue | Cause | Fix | Time Spent |
|-------|-------|-----|-----------|
| `tab-more` testID not found | Expo Router `tabBarTestID` not exposed to Maestro on iOS 26 | Switch to point-based taps | ~10 min |
| Tab taps at `97%` hit toast | iOS 26 persistent location error toast covers tab bar | Change to `95%` vertical | ~5 min |
| Back button at `5%,6%` missed | Dynamic Island pushes interactive area down | Change to `10%,10%` | ~5 min |
| `assertVisible: "Business Dashboard"` failed | TouchableOpacity concatenates child text in accessibility tree | Use regex `"Business Dashboard.*"` | ~5 min |
| `"Discover & Create"` not found on Add screen | Section header text was `"Core Actions"` and `"Create Content"` | Read actual source code | ~3 min |
| `"Create Community"` assertion wrong | Actual string is `"Create a Community"` (from strings.ts) | Read strings constant | ~2 min |
| Dashboard shows empty state | RestaurantContext doesn't load for test user (migration not deployed) | Make assertions optional | ~5 min |

**Total debugging time**: ~35 min (more than the implementation itself)

**Root cause**: The E2E test generation step has no feedback loop with the actual device. Tests are written based on source code assumptions but the runtime accessibility tree often differs.

### 2. Agent-Generated E2E Tests Were Unusable Stubs
The 2 E2E tests generated by implementation agents (`no-beta-gate.yaml`, `no-communities-for-business.yaml`) both:
- Used `id: "tab-more"` which doesn't work on iOS 26
- Used exact text selectors that don't match concatenated accessibility labels
- Didn't handle the persistent toast overlay
- Didn't follow production test patterns (point-based taps, dismiss-toast helper)

**The agents wrote tests based on the React Native code, not the Maestro-visible accessibility tree.**

### 3. Dashboard Quick Actions Not Testable Without Deployed Migration
The TRO-170 "Claim Location" quick action only appears when `dashboardData` loads, which requires the `business_profiles` migration to be deployed. Test accounts showed empty dashboard state.

### 4. No Way to Verify Realtime Subscription in E2E
TRO-162 (claim approval refresh via AppState + realtime) can't be tested with Maestro because:
- Can't simulate `AppState` background/foreground transitions
- Can't trigger a Supabase realtime event from a Maestro flow
- Would need a secondary process to update the database mid-test

## Patterns Discovered

### Maestro iOS 26 Cheat Sheet

```yaml
# Tab bar positions (iPhone 17 Pro, 95% vertical to avoid toast)
Home:     point: "10%,95%"
Explore:  point: "30%,95%"
Add:      point: "50%,95%"
Activity: point: "70%,95%"
More:     point: "90%,95%"

# Back button (Dynamic Island devices)
Back:     point: "10%,10%"

# Text inside TouchableOpacity: use regex
- assertVisible:
    text: "Business Dashboard.*"    # matches concatenated accessibility label

# Standalone section headers: use exact text
- assertVisible:
    text: "Business Tools"          # standalone <Text> element

# Always dismiss toast before tab navigation
- runFlow: ../../helpers/dismiss-toast.yaml

# Dismiss Expo error overlay (dev builds only)
- tapOn:
    text: "Dismiss"
    optional: true
```

## Optimization Roadmap

### Short-Term (Next Batch)

#### 1. **Maestro Test Template with Device-Aware Selectors**
Create `e2e/templates/v1017-patterns.yaml` that agents import. Include:
- Correct point-based tab positions for the current device
- Toast dismiss helper calls
- Error overlay dismiss
- Regex-based text assertions

#### 2. **Pre-Flight E2E Validation Step**
Before writing tests, run a quick Maestro `takeScreenshot` after login to capture:
- Actual tab bar positions
- Visible text elements
- Accessibility tree dump
Then use those findings to write tests, not source code assumptions.

#### 3. **Deploy Migrations Before E2E Tests**
The implementation agents finish → merge code → push migrations → THEN write/run E2E tests. The current flow writes E2E tests before migrations are deployed, causing false failures.

### Medium-Term (Next 2-3 Batches)

#### 4. **Automated E2E Test Runner Agent**
A dedicated agent that:
- Takes a feature description + modified files list
- Runs Maestro `takeScreenshot` on each affected screen
- Reads the screenshots to identify actual visible elements
- Writes tests grounded in the REAL accessibility tree
- Runs tests and iterates until passing
- Has a max iteration budget (5 attempts)

#### 5. **Accessibility Tree Dump Tool**
Build a helper that dumps the Maestro-visible accessibility hierarchy to a JSON file:
```bash
maestro hierarchy > /tmp/hierarchy.json
```
Agents can read this instead of guessing from React Native source.

#### 6. **Test Data Bootstrapping for E2E**
Create a pre-test SQL script that ensures test accounts have the right data for ALL features being tested. Run it before the E2E suite:
```bash
node scripts/run-prod-sql.js e2e/fixtures/ensure-test-data.sql
maestro test e2e/flows/v1017/
```

### Long-Term (Architecture)

#### 7. **Closed-Loop E2E Generation**
The dream pipeline:
```
/groom → /approve → implement (agents) → deploy migrations →
E2E agent captures screenshots → writes tests from screenshots →
runs tests → iterates → all green → commit
```

Key insight: **E2E tests should be written from device screenshots, not source code.** The accessibility tree is the contract, not the JSX.

#### 8. **Unified Test Artifact Schema**
Standardize all testing outputs:
```
testing/
  {feature-name}/
    manual-test.md       # Human walkthrough
    verify.sql           # DB verification
    reset.sql            # DB cleanup
    e2e/                 # Maestro flows
      {scenario}.yaml
    screenshots/         # Reference screenshots
      {step}.png
```

#### 9. **Migration Deployment Pipeline**
Automate migration deployment as part of the spec execution:
```
/execute → implement → typecheck → lint →
push dev migration → verify dev →
push prod migration → verify prod →
run E2E → commit
```

## Key Takeaway

The biggest bottleneck in AI-native development is **not code generation** (that works well with parallel agents + worktrees). The bottleneck is **E2E test generation**, because tests must match the **runtime accessibility tree** which differs from the source code in unpredictable ways (concatenated labels, missing testIDs, platform-specific rendering, overlapping UI elements like toasts).

The fix is to close the loop: let the testing agent **see the actual device state** before writing assertions. This is achievable with Maestro's screenshot + hierarchy tools and would transform E2E testing from a multi-iteration debugging session into a one-shot generation.
